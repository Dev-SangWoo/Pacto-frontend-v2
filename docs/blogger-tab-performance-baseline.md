# 블로거 탭 전환 성능 기준선

## 측정 목적

블로거 앱의 홈, 미션, 지갑, 내 정보 탭 전환 지연을 재현하고 개선 전후를 같은 조건에서 비교한다.

## 기준선 환경

- 측정일: 2026-07-21
- 실행 방식: `next dev` (`apps/blogger`, port 3000)
- API: `https://pacto-api.duckdns.org`
- 근거: 개발 서버 터미널에 출력된 Next.js 요청 처리 시간과 API 요청 로그
- 주의: Next.js의 링크 prefetch는 개발 모드에서 동작하지 않으므로 배포 빌드보다 느릴 수 있다.

## 개선 전 기록

| 화면                      |  관찰된 시간 | 비고                                        |
| ------------------------- | -----------: | ------------------------------------------- |
| 홈 `/campaigns` 최초 요청 |      1,364ms | Next.js 150ms, 애플리케이션 코드 1,213ms    |
| 홈 `/campaigns` 반복 요청 | 약 164~394ms | 동일 API를 매번 다시 호출                   |
| 환경 변수 재로딩 직후 홈  |        777ms | Next.js 277ms, 애플리케이션 코드 500ms      |
| 내 정보 `/profile`        |      2,600ms | `/auth/me`와 알림 요청의 403 응답 대기 포함 |
| 권한 오류 `/forbidden`    |        118ms | 오류 판정 이후 화면 자체는 빠름             |

위 수치는 브라우저 Performance API로 수집한 정밀 지표가 아니라 기존 서버 로그에서 확보한 기준선이다. 절대값보다 동일 조건에서의 개선 전후 비교에 사용한다.

## 발견한 병목

1. 공통 API 클라이언트가 모든 요청에 `cache: no-store`, `revalidate: 0`을 적용한다.
2. 공통 레이아웃이 사용자 이름과 알림 개수를 위해 세션을 중복 조회한다.
3. 알림 개수를 구하기 위해 알림 목록 전체 페이지를 순회한다.
4. 미션과 지갑은 목록을 받은 뒤 캠페인 상세를 캠페인 수만큼 추가 조회한다.
5. 지갑은 지갑/내역 조회 후 미션 조회를 시작하는 직렬 구간이 있다.
6. 동적 화면에 로딩 경계가 없어 서버 응답 전까지 탭 클릭이 반영되지 않은 것처럼 보인다.

## 1차 개선 범위

- 하단 네비게이션의 네 개 탭을 명시적으로 prefetch한다.
- 공통 `loading.tsx` 스켈레톤으로 탭 클릭에 즉시 반응한다.
- 공개 캠페인 목록만 30초간 서버 캐시한다.
- 지갑, 포인트 내역, 미션 목록 요청을 동시에 시작한다.
- 공통 레이아웃에서 세션을 한 번만 읽는다.
- 미션, 지갑, 프로필, 알림처럼 사용자별 최신 상태가 중요한 데이터는 장기 캐시하지 않는다.

## 재측정 절차

1. `pnpm --filter @pacto/blogger build` 후 프로덕션 모드로 실행한다.
2. 로그인 후 홈 → 미션 → 지갑 → 내 정보 → 홈 순서로 한 번 이동해 각 경로를 준비한다.
3. 같은 순서로 두 번째 이동하면서 브라우저 Network의 문서/RSC 요청 시간과 서버의 `GET /경로 ... in Nms`를 기록한다.
4. 캐시가 비어 있는 최초 전환과 준비된 반복 전환을 구분해 각각 5회 측정한다.
5. 평균뿐 아니라 가장 느린 값도 기록한다.
