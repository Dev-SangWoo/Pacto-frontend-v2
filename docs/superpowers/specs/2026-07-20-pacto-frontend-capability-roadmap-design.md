# Pacto 프론트엔드 역량 강화 로드맵 설계

## 1. 목적

Pacto의 실제 서비스 품질을 높이는 동시에, 문제 발견부터 검증까지의 사고 과정이 코드, 테스트, 문서, 커밋에 남도록 한다.

기술을 체크리스트처럼 추가하지 않는다. 실제 병목과 도메인 위험을 먼저 확인하고, 문제 해결에 필요한 기술만 선택한다. 각 개선은 다음 구조로 설명할 수 있어야 한다.

```text
문제 → 기준선 → 원인 분석 → 대안 비교 → 선택 → 구현 → 검증 → 결과와 한계
```

기간은 6~8주를 기준으로 하며, Blogger 성능, 핵심 거래 E2E, Dashboard 구조와 번들, 접근성과 디자인 시스템, AI 품질 가드 순서로 진행한다.

## 2. 설계 원칙

### 2.1 문제와 측정 중심

- 도구 도입 자체를 목표로 삼지 않는다.
- 한 번에 하나의 주요 가설을 검증한다.
- 변경 전후를 같은 조건에서 측정한다.
- 기대한 개선이 없었던 실험도 원인과 다음 판단을 기록한다.
- Server Component 중심인 현재 구조의 장점을 유지한다.

### 2.2 서비스와 포트폴리오의 균형

- 실제 사용자 흐름과 도메인 위험을 우선한다.
- 성능 수치, Profiler 결과, 번들 변화, 테스트 시나리오를 증거로 남긴다.
- 기술 이름보다 선택 이유와 트레이드오프를 설명한다.
- 과장된 성과 표현을 피하고 측정 환경과 한계를 함께 밝힌다.

### 2.3 변경 격리

- 한 커밋에는 하나의 의도만 담는다.
- 사용자 작업 중인 변경을 덮어쓰거나 함께 커밋하지 않는다.
- 성능, 상태, 테스트, 접근성 변경을 가능한 한 독립적으로 검증한다.
- 도메인 규칙은 `packages/types`, `packages/api`, `packages/utils` 경계를 유지한다.

## 3. 현재 상태

Pacto는 Next.js App Router 기반 pnpm 모노레포다.

```text
apps/blogger      블로거용 모바일 웹
apps/dashboard    대행사·광고주용 대시보드
packages/api      API service와 adapter
packages/types    도메인 타입
packages/utils    상태·포맷 도메인 규칙
packages/ui       공용 UI
```

현재 강점은 다음과 같다.

- Blogger와 Dashboard의 사용자 경험 분리
- API 원본 응답과 화면 타입 사이 adapter 경계
- 상태 변환, 금액 포맷, API 계약을 검증하는 Vitest 테스트
- Lighthouse 기준선과 이미지 최적화 기록
- 시맨틱 태그와 ARIA 속성 적용
- 이미지 포맷 변경, 요청 중복 제거, 초기 조회 범위 축소 경험

현재 보완이 필요한 영역은 다음과 같다.

- README에 명시된 TanStack Query와 Playwright가 실제 의존성·구현과 일치하지 않는다.
- React Profiler, Bundle Analyzer, 운영 Web Vitals 수집이 체계화되지 않았다.
- Storybook과 접근성 자동 검사가 없다.
- 서버, URL, 전역, 로컬 상태의 선택 기준이 문서화되지 않았다.
- AI 활용 시 컨텍스트 범위와 승인 기준이 정의되지 않았다.

## 4. 6~8주 단계별 로드맵

### 4.1 1단계: 성능 기준선과 측정 체계

기존 Lighthouse 보고서는 운영 배포 기준선이 아니다. 실제 보고서의 대상은 `localhost:3000`, `localhost:3001`이며 Blogger 로그인 보고서만 로컬 네트워크 주소를 사용한다.

따라서 기존 수치는 `local exploratory baseline`으로 분류한다. 개발 서버와 production build 서버의 구분도 기존 문서만으로 명확하지 않으므로, 포트폴리오 최종 성과 수치로 직접 사용하지 않는다.

새 기준선은 다음 조건으로 만든다.

- 실제 배포 URL 사용
- 동일한 로그인 상태와 테스트 데이터 사용
- 동일한 모바일 기기·네트워크 프로필 사용
- 페이지별 최소 3회 측정 후 중앙값 기록
- 측정 시점의 커밋 SHA와 배포 URL 기록
- 로컬 수치와 배포 수치를 직접 비교하지 않음

측정 대상은 LCP, CLS, INP, Lighthouse Performance, 긴 메인 스레드 작업, 컴포넌트 렌더 횟수, 라우트별 초기 JavaScript 크기, API 중복 요청 수다.

초기 목표는 다음과 같다.

| 항목                             |                                    목표 |
| -------------------------------- | --------------------------------------: |
| Blogger 핵심 화면 LCP            |                         2.5초 이하 지향 |
| CLS                              |                                0.1 이하 |
| INP                              |                         200ms 이하 지향 |
| Blogger Lighthouse Performance   |         핵심 화면 80 이상, 이후 90 도전 |
| Dashboard Lighthouse Performance | 기존 로컬 90 이상 수준의 운영 회귀 방지 |

### 4.2 2단계: Blogger 성능과 검색

캠페인 탐색을 대표 개선 사례로 사용한다.

- 검색 입력에 debounce 적용
- 한글 IME 조합 상태 고려
- `AbortSignal`로 이전 요청 취소
- 응답 순서 역전 방지
- 검색어와 필터를 URL 상태로 표현
- 첫 화면 이미지에만 적절한 우선순위 지정
- 화면 밖 이미지는 lazy loading
- 실제 번들 근거가 있는 기능만 dynamic import
- Profiler 근거가 있는 경계만 memoization

React Query는 모든 조회에 적용하지 않는다. Server Component가 최초 데이터를 제공하는 구조를 유지하고, 사용자가 자주 갱신하거나 여러 컴포넌트가 일관되게 공유해야 하는 서버 상태에만 사용한다.

후보는 캠페인 검색·필터, 지원자 승인 후 목록 갱신, 미션 상태 변경, 지갑 거래 내역 페이지네이션이다. 검색어, 모달 열림, 선택 행은 서버 상태가 아니므로 React Query에 넣지 않는다.

### 4.3 3단계: 핵심 거래 E2E

Playwright로 다음 사용자 흐름을 보호한다.

```text
캠페인 생성과 노출
→ 블로거 지원과 대행사 승인
→ 미션 제출과 검수
→ 에스크로 정산과 지갑 반영
→ 출금 신청
```

거대한 단일 테스트 대신 단계별 시나리오로 나눈다.

- 캠페인 생성·노출
- 지원·승인과 중복 지원 차단
- 미션 제출·검수와 잘못된 상태 전이 차단
- 정산·지갑 잔액 반영
- 역할과 소유권 기반 접근 차단

테스트 환경은 세 계층으로 구분한다.

| 환경             | 목적                              |
| ---------------- | --------------------------------- |
| local mock       | 빠른 UI 회귀 확인                 |
| staging          | 실제 백엔드 계약과 상태 전이 확인 |
| production smoke | 읽기 중심의 최소 운영 검증        |

실제 결제와 출금 변경 시나리오는 production에서 실행하지 않는다. 테스트 전용 계정, 고유 데이터, seed 또는 fixture를 사용하며 임의 시간 대기 대신 화면 상태와 네트워크 완료 조건을 기다린다.

### 4.4 4단계: Dashboard 상태와 번들

상태의 소유권을 다음처럼 분리한다.

| 상태                 | 예시                              | 위치                                   |
| -------------------- | --------------------------------- | -------------------------------------- |
| 서버 상태            | 캠페인, 미션, 지갑                | Server Component 또는 React Query      |
| URL 상태             | 검색어, 필터, 페이지              | search params                          |
| 로컬 UI 상태         | 모달, 선택 행, 보기 방식          | `useState`                             |
| 폼 상태              | 캠페인 생성, 출금 신청            | 폼 상태 또는 action state              |
| 전역 클라이언트 상태 | 여러 비연관 영역의 최소 공유 상태 | 실제 필요가 확인될 때만 Context·스토어 |

Bundle Analyzer로 Tiptap, 아이콘, 공용 패키지, 큰 Client Component를 확인한다. Tiptap 편집기는 편집 화면에서만 로드하는 것을 우선 검토한다. 동적 로딩에는 크기가 고정된 fallback과 오류 처리를 제공한다.

React Profiler로 캠페인 목록, 지원자 목록과 상세 패널, 캠페인 모바일 미리보기를 분석한다. `memo`, `useMemo`, `useCallback`은 렌더 비용과 props 안정성 문제가 확인된 경우에만 적용한다.

### 4.5 5단계: 접근성, 디자인 시스템, Storybook

키보드만으로 캠페인 탐색, 지원, 승인, 미션 제출, 지갑 확인, 출금 신청을 완료할 수 있어야 한다.

핵심 기준은 다음과 같다.

- 이동은 링크, 실행은 버튼 사용
- 입력과 오류 메시지 연결
- 모달 포커스 진입·순환·복귀
- `:focus-visible` 제공
- 색상 외 상태 표현 제공
- 상태 변경을 과하지 않게 보조 기술에 전달
- 금액의 available·locked 의미를 텍스트로 구분

디자인 시스템은 반복성과 상태 복잡도가 높은 요소부터 시작한다.

```text
Button, FormField, Input, StatusBadge, Dialog,
EmptyState, ErrorState, Skeleton, MoneyDisplay, InlineAlert
```

Storybook은 페이지 복제가 아니라 컴포넌트 상태와 상호작용 문서화에 사용한다. 기본, 로딩, 비활성, 오류, 긴 한글, 좁은 화면, 키보드 동작을 포함한다.

자동 검사는 ESLint·Storybook·Playwright 접근성 검사와 수동 키보드 검증을 조합한다. 동일한 문제가 반복될 때만 커스텀 규칙으로 승격한다.

### 4.6 6단계: AI 품질 가드

AI는 반복 코드 탐색, 컴포넌트 분리 후보, Story와 테스트 초안, 누락 상태 탐지, PR 리뷰에 사용한다. 승인 권한은 갖지 않는다.

AI 작업에는 다음 컨텍스트 패킷을 제공한다.

```text
작업 목적
관련 사용자 흐름
관련 파일과 정책 문서
변경 허용 범위
변경 금지 영역
성공 기준
실행할 검증
알려진 위험
```

위험도별 승인 기준은 다음과 같다.

| 위험도    | 예시                       | 승인 기준                        |
| --------- | -------------------------- | -------------------------------- |
| 낮음      | 문구, Story 초안           | lint와 시각 확인                 |
| 보통      | 컴포넌트 분리, 캐시 변경   | 테스트, Profiler, 코드 검토      |
| 높음      | 권한, 상태 전이, 정산 금액 | 단위·통합·E2E와 수동 도메인 검토 |
| 매우 높음 | 실제 결제·출금 호출        | 별도 환경과 명시적 운영 승인     |

Figma MCP는 프레임을 그대로 복제하는 도구가 아니라 디자인 토큰, variant, 반복 구조를 읽어 기존 `packages/ui`와 대응시키는 도구로 사용한다. 생성 초안은 반응형, 오류·로딩 상태, 시맨틱 구조, 키보드 동작을 사람이 보완한다.

## 5. 성능 분석 절차

### 5.1 Chrome DevTools Performance

캠페인 화면의 새로고침, 검색, 필터 전환, 보기 방식 전환, 상세 진입을 녹화한다. 긴 JavaScript 작업, hydration, 스타일·레이아웃 반복, 이미지 디코딩, 네트워크 순서를 확인한다.

### 5.2 React Profiler

다음 질문을 기준으로 렌더링 원인을 확인한다.

- 검색 입력 한 번에 어떤 컴포넌트가 렌더링되는가?
- 보기 방식 변경 시 모든 카드가 다시 렌더링되는가?
- 지원자 선택 시 목록 전체가 다시 렌더링되는가?
- 렌더 시간이 실제 사용자 지연에 영향을 주는가?

### 5.3 Lighthouse와 Web Vitals

Lighthouse는 통제된 실험실 측정으로 사용하고, 운영 Web Vitals는 실제 사용자 환경을 확인하는 자료로 사용한다. 두 수치를 같은 것으로 취급하지 않는다.

### 5.4 Bundle Analyzer

라우트별 초기 JavaScript와 큰 모듈을 기록한다. 분리 전후 번들 크기뿐 아니라 LCP, INP, 로딩 경험을 함께 검증한다.

## 6. 테스트 전략

### 6.1 단위 테스트

상태 전이, 버튼 활성화 조건, 금액 계산, API adapter, 오류 메시지 변환처럼 빠르고 결정적인 도메인 규칙을 검증한다.

### 6.2 통합 테스트

MSW와 Testing Library로 검색 성공·실패·빈 상태, mutation 후 갱신, 중복 제출 방지, 폼 오류 유지, 접근성 이름과 키보드 조작을 검증한다.

### 6.3 E2E 테스트

실제 브라우저에서 사용자 결과를 검증하며 내부 구현이나 CSS 클래스에 과도하게 의존하지 않는다. 역할과 접근성 이름 기반 selector를 우선한다. 실패 시 screenshot, trace, video를 보관한다.

### 6.4 CI 계층

```text
모든 PR:
lint → typecheck → unit test → build

핵심 흐름 변경:
integration test → 핵심 E2E

정기 실행:
전체 E2E → Lighthouse 회귀 → 접근성 검사 → 번들 리포트
```

성능 검사는 초기에는 보고서만 생성한다. 반복 데이터가 쌓인 뒤 환경 변동을 고려한 허용 범위를 정한다.

## 7. 기록과 Git 전략

### 7.1 문서 구조

```text
docs/performance/
├─ baselines/
├─ investigations/
├─ results/
└─ README.md
```

개선 기록에는 다음 내용을 포함한다.

- 측정 환경과 커밋 SHA
- 사용자 재현 시나리오
- 변경 전 수치
- 도구로 확인한 원인
- 검토한 대안과 선택 이유
- 변경 내용
- 변경 후 수치
- 부작용과 남은 작업
- 관련 커밋과 PR

### 7.2 커밋 원칙

- 제목은 변경 결과를 한글로 요약한다.
- 본문은 문제, 선택 이유, 검증 결과를 설명한다.
- 성능 수치는 측정 조건과 함께 적는다.
- 테스트 커밋은 막으려는 도메인 위험을 드러낸다.
- AI 사용 여부보다 변경의 기술적 의도를 제목에 둔다.

예시 흐름:

```text
docs(perf): 캠페인 탐색 배포 성능 기준선 기록
test(campaign): 검색 응답 순서 역전 시나리오 재현
perf(campaign): 이전 검색 요청 취소 적용
test(e2e): 캠페인 지원 승인 상태 전이 검증
docs(perf): 캠페인 탐색 성능 개선 결과 기록
```

중요 커밋 본문 예시:

```text
perf(campaign): 검색 요청 횟수와 응답 역전 방지

연속 입력 시 모든 검색어가 즉시 요청되어 불필요한 호출이
발생했고, 이전 응답이 늦게 도착하면 최신 결과를 덮어쓸 수 있었다.

300ms 입력 지연과 AbortSignal 기반 요청 취소를 적용했다.

검증:
- 검색 E2E 통과
- 동일 시나리오 요청 수 전후 비교
- 배포 환경 INP 중앙값 전후 비교
```

### 7.3 PR 기록

PR에는 작업 내용, 문제 근거, 검토한 대안, 확인 방법, 측정 결과, 남은 위험을 포함한다. AI를 사용했다면 초안 생성 범위, 사람이 내린 결정, 자동·수동 검증을 추가한다.

## 8. 성공 기준

다음 조건을 만족하면 로드맵이 성공한 것으로 본다.

- 로컬과 배포 성능 기준선이 명확히 구분된다.
- Blogger 핵심 화면의 병목이 도구 근거와 함께 개선된다.
- 핵심 거래 흐름과 권한 정책이 E2E로 보호된다.
- 서버, URL, 로컬, 전역 상태의 경계가 코드와 문서에서 일치한다.
- 무거운 Dashboard 기능의 번들 비용과 로딩 전략이 검증된다.
- 핵심 흐름을 키보드로 완료할 수 있다.
- 공용 컴포넌트의 주요 상태가 Storybook에 문서화된다.
- AI 변경이 위험도별 승인과 검증 절차를 따른다.
- 커밋과 PR만 읽어도 문제와 판단 과정을 추적할 수 있다.
